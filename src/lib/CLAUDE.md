# src/lib: watcher, signals and shared modules

Path-bound rules for `src/lib/` (and `src/lib/signals/`). Cross-cutting rules, commands and the state file table: root `CLAUDE.md`. Run/improve pipeline steps: `src/steps/CLAUDE.md`. Prompt templates: `src/prompts/CLAUDE.md`.

## Inbound links

**inbound links** (`src/lib/inbound-links.js`, `src/steps/link-judge.js`, `buildInboundLinkFiles`/`tryInboundLinkFiles` in `lib/landings.js`, `src/commands/links.js`; switch `inbound_links: false`, default on): a new page linked out but nothing linked to it (13 of about 30 pages had fewer than 3 inbound links, 4 had none). Code decides eligibility, a model only judges topic. `eligibleSources` (pure) takes pages of the same locale that are not the target, do not link to it yet and have fewer than 4 `related_pages` (the cap `generate.md` asks for) and a form `addRelatedPage` can edit (no inline list, no CRLF). A token-overlap gate was tried first and dropped: title boilerplate (`ablauf`, `checkliste`, `price`) drove the picks even after filtering site-generic tokens. `judgeLinkSources` makes ONE `complete()` call per target with `MODELS.judge` (Haiku 5.5, `claude.js` sets thinking to `disabled` for it), prompt `link-judge.md` (slug, title and meta description per candidate in an untrusted block, no body), score 0 unrelated / 1 adjacent / 2 same need, the model lists only 1 and 2 (omitted = 0, `maxTokens` = min(8000, 256 + 48 per candidate)); code keeps only score 2, drops slugs not in the candidate list, prefers pages with fewer `related_pages` (no hubs), then input order, and takes `max`. The reason (at most 8 words) goes into the PR body. Invalid JSON gets one retry, then no links and a warning; any other judge error becomes the warning `Inbound links skipped` in `tryInboundLinkFiles`, the PR ships without the extra files. `addRelatedPage` is a text edit like `repointRelatedPages`: it appends to the existing list in its own style or inserts the list before the closing `---`. `createPRs` adds the edits of each new page to the PR files (`exclude` = the PR's own pages plus sources an earlier PR of the same run already edits, since sibling PRs branch from one checkout), `prepareImprove` does the same for a rewritten page with fewer than 3 inbound links (pages in the PR or deleted by a merge are neither edited nor counted). `seo links` plans all pages of the default and counterpart locale below 3 inbound links in one PR on `seo/links/<week>` and prints the LLM cost (existing branch: warning, exit 0; nothing to do: no PR; `--dry-run` writes no PR or page, but the judge calls are booked in `seo/budget.json`).

## Watcher (`seo watch`) and index alerts

**index-check** (`src/steps/index-check.js`, `src/commands/index-status.js`): Inspects the live Google index state of every sitemap URL (150 ms apart, `fetchSitemapUrls` throws on a non-2xx answer or a body without `<urlset>`/`<sitemapindex>`, so a broken sitemap is a failed check, never an empty one; capped at 500, well inside the URL Inspection API quota of 2000/day and 600/min per property); a 5xx from Google is retried once after 5 s, a second failure fails the check and diffs it against `seo/index-status.json` from the previous run, reporting newly dropped, newly indexed and still-missing URLs. It exists because `zeit.rafaelalex.de` lost its whole index on 2026-08-04 and nobody noticed for five weeks: a quiet week and a silently deindexed one both print "nothing to do". A first run writes a baseline rather than claiming everything just dropped. `--commit` (the workflow now goes through `seo watch --commit` instead) pushes the snapshot straight to `main` through `commitState`, with `[skip ci]` in the message because portfolio-2025 deploys to FTP on every unfiltered push.

**watch** (`src/steps/watch.js`, pure rules in `src/lib/watch.js`, `src/commands/watch.js`): the daily guard, no LLM, no SerpAPI, no budget. Runs `checkIndexStatus`, then compares landing page impressions of the last 7 complete days (ending today-3) with the 7 days before (`queryPageTotals` with `pageFilter: base_url`, rows mapped by `urlToSlug`). State in `seo/alerts.json`: `open` alerts (index alerts also carry `diagnosis`, see diagnose), `known_indexed` (URLs ever seen indexed), `traffic_pending`, `failures`, `last_resubmit`. `deindexed:<url>` comes from the current state (known_indexed but not indexed now), not from the daily diff, and resolves when indexed again. `site_not_indexed` is the site-level alert, independent of `known_indexed` so it fires on the first snapshot: with at least 5 judged URLs (`unknown` excluded) it opens below 20 percent indexed (detail `{ indexed, total }`) and resolves from 50 percent, in between it keeps its state. `traffic_drop` opens after 2 consecutive days over 40 percent loss at 200+ impressions in the comparison window and stores the compared volume as `reference`; it resolves once the week is back at 75 percent of that reference, also when the week fell under 200 impressions, and a day under the floor resets the pending count. `known_indexed` is pruned to the current sitemap, and a `deindexed` alert whose URL left it resolves with `reason: removed_from_sitemap`. A failed check (GSC or auth error) leaves its alerts alone and counts as a failure (2 in a row open `watch_blind`); it goes into `errors`, makes the report status `failed` and the command exit non-zero, but only after alerts, report and `--commit` are done. `--dry-run` writes neither `alerts.json` nor `index-status.json`. `unknown` index entries (quota) never overwrite the previous entry (`saveIndexStatus`), which also keeps `updated` stable when the entries are equal; entries that differ only in `lastCrawlTime` count as equal and keep the old one, so a recrawl alone makes no state commit. Status `alert` (opened or diagnosis changed), `resolved`, `watch_ok`. `--commit` goes through `commitState({ files })` with only `seo/alerts.json` and `seo/index-status.json`, so a quiet day makes no commit. The watcher writes no run log; `seo run` and `seo improve` write `seo/last-run.json` and `seo/runs.jsonl` (52 lines) through `writeRunLog` in `src/lib/runlog.js` before their last `commitState`. **ai crawlers and structured data** (`src/lib/ai-crawlers.js`, `src/lib/structured-data.js`, evaluators `evaluateAiCrawlers`/`evaluateStructuredData` in `src/lib/watch.js`, `checkCrawl` in `src/steps/watch.js`; switches `watch.ai_crawlers`/`watch.structured_data`, default on, set `false` to turn off): inputs `aiCrawlers`/`structuredData` of `evaluateWatch` follow the Bing convention (`null` untouched, `{ disabled: true }` closes the alerts by `kind` with reason `<check>_disabled`). `ai_crawler_blocked` is about the search bots in `AI_BOTS` (training bots only in `report.ai_crawlers`): robots.txt (exact token group before `*`, longest path wins, Allow wins a tie, any 4xx allows all, 5xx unknown; judged against `/` and all sitemap paths, only for bots with `robots: true`) opens at once; the live check (home plus one rotating sitemap URL per bot UA and a browser UA, blocked = status >= 400 or challenge while the browser gets 2xx) opens on the second run in a row and only for a token in `ai_crawlers.ok_seen` (set once when the bot was live `ok`), else a warning. `structured_data` fetches up to 10 landing pages a day (`bingSection(urls, today, 10)`; without `landing_path` the sitemap URLs, slug = path, and a failed index check leaves the alert untouched) plus those with an open or pending finding and opens a slug on the second run in a row (`pageCheck`: `jsonld_missing`, `jsonld_invalid`, `required:<Type>.<field>` from the per-type rules in `fieldGaps` (Recipe, LocalBusiness and its common subtypes, Product with Offer/AggregateRating/Review, Event, BreadcrumbList, VideoObject, SoftwareApplication, ProfilePage, WebSite; field lists from Google's structured data docs), plus `meta_noindex` (meta robots/googlebot or `X-Robots-Tag`) and `canonical_other` from `src/lib/onpage.js`, both only for a page in the sitemap: a landing page the site keeps out of it is excluded on purpose (zeit's noindex guides), and with the sitemap unknown such a page stays undecided; cut-off body, non-2xx or no `<html`/`<title` is unknown). Recommended gaps (`jsonld_missing` on a sitemap-discovered page without `landing_path`, SoftwareApplication `aggregateRating|review`, FAQ items in the frontmatter without a `FAQPage` type, report only since Google dropped FAQ rich results in June 2026; Google's non-critical issues, Article and Organization fields, missing meta description, canonical, `html lang`, og:title/description/image, missing or doubled h1, WebSite and Organization/Person entity on the home page) only land in `report.structured_data.recommended` as `[{ slug, fields }]`, never in state or alerts. One shared fetch pool (concurrency 5, deadline 60 s, injectable `fetchBot` and `crawlDeadlineMs`); undecided fetches change nothing and warn. State holds only `ai_crawlers.{pending, ok_seen}` and `structured_data.pending`, no report, so identical runs leave `alerts.json` byte-equal. A changed `detail` of an open alert is returned as `updated` and lands in `report.alerts.updated`. Neither check counts towards `failures` or `errors`.

The reusable workflow takes `mode` (`run`|`watch`); in run mode `seo watch --commit` replaces the old `index-status --commit` step.

**diagnose** (`src/lib/diagnose.js`, `src/steps/diagnose.js`) and **assess** (`src/steps/assess.js`, prompt `src/prompts/assess.md`): index alerts explain themselves. `seo watch` runs `diagnoseAlerts` after `evaluateWatch` (and after a first `saveAlerts`) with the `entries` of `checkIndexStatus`, none when the index check failed. For at most 10 distinct URLs (round-robin across the open alerts) of the open `deindexed`/`site_not_indexed` alerts it fetches the page as Googlebot (`fetchForDiagnosis`, `safeFetch`, 10 s timeout, `Accept-Language`) and `robots.txt` once, and `diagnoseUrl` (pure) returns finding codes with a fixed English `fix` text. `cause` is `technical` when a live code with that effect applies, else `unknown` (5xx, 401/403/429, failed fetch, missing or `unknown` inspection entry), else `clean`; Google hints (`google_canonical_other`, `robots_blocked`, `google_fetch_failed`, `soft_404`, from the stored `googleCanonical`/`pageFetchState`) never decide, since they can linger until the next crawl. The diagnosis is merged into the alert object (`opened` and `open` share it; `assessment` and `resubmitted_at` stay). An `unknown` result keeps the old diagnosis, a changed `cause`/`codes` needs two runs in a row (`pending_codes`), the first diagnosis counts at once, and `checked_at`/`urls` move only on a change, so quiet days do not commit. The first diagnosis of an alert that was already open and a later change of it land in `report.alerts.updated` (an alert opened in the same run is listed only under `opened`) and makes the status `alert`. A `clean` alert without `resubmitted_at` triggers `submitFixes` (sitemap via `submitSitemap`, IndexNow with `indexnow_key`) once per run, at most every 7 days (`last_resubmit`), never in a dry run. Diagnosis and resubmit failures are warnings, never errors. `watch()` takes injectable `diagnose` and `submit` so tests stay off the network. `seo run` calls `assessAlerts` right after `measure`: for `clean` alerts without `assessment` or older than 28 days, `site_not_indexed` first, at most 3 Sonnet calls (alerts with the `no_text` hint are skipped with a warning; a result without actions is a failed call, nothing saved; page text of the first URL in an untrusted block), stored as `alert.assessment` after stripping markup and URLs; a dry run only prints, a failure is a warning, `BudgetExceededError` propagates. The assessment is written in German for the owner and receives the seo PRs merged in the last 56 days (`changes.json`) as `recent_changes`; the assessment also gets `today`, and a change flagged `revert_candidate` is marked in that list; `seo run` and `seo watch` reports carry `site` (`siteInfo` in `lib/config.js`). The assessment waits for a recrawl: an alert is not assessed while its newest `changes.json` merge is less than 28 days old and no URL of the alert has a `lastCrawlTime` after that merge day. The last change is per alert (entries whose `urls` contain one of the alert's URLs, slashes trimmed), except for `site_not_indexed`, which takes the newest merge of all. Because the stored crawl times lag, a waiting alert re-inspects its URLs live (injectable `inspect`, at most 10 URLs, one call per waiting alert, nothing written to `index-status.json`; a failure is the warning `Assessment: live crawl check failed for <id>` and the alert keeps waiting); the 28-day bound stays. Waiting alerts land in `report.assessments_waiting`. The prompt also gets the same-host links of the page and of the home page as `page_links` (`internalLinks`) and the target repo's commit subjects of the last 56 days as `recent_commits` (`git log -n 300` filtered afterwards, no `seo:`/`[skip ci]` commits, at most 30; links and commits are fenced as untrusted blocks, `internalLinks` drops only known asset extensions, a failed home fetch warns and is noted in the list; the workflow checks out with `fetch-depth: 200`). `report.assessments` goes to the notify payload (`seo-reusable.yml`). `assessments_waiting` goes there too. **Content owners** (`content_owners: [{ name, paths }]`, `src/lib/content-owners.js`, default `[]`): when every URL of an alert sits under one owner's path prefixes (`/shop/` covers `/shop` and `/shop/x`, not `/shopping`), the prompt says that person writes the page text and the schema asks for `audience` (`content`/`site`) per action; the assessment then carries `content_owner` and each action its `audience` (missing or invalid = `site`), so the notify mail lists the `content` actions in a block to forward. Without a matching owner prompt, schema and result are unchanged. **Assessed rewrite** (`src/lib/assessed-rewrite.js`): an assessment is not a to-do list for the owner, it is carried out. The assess prompt lists the translation pairs (`alternate:`, `counterpartPairs`; they were taken for duplicates) and, for pages without a content owner, limits the actions to what a rewrite of the page itself can do (no merge, redirect, edits on other pages, Search Console or "wait"). `prepareImprove` picks, after the season page and before the GSC pick, the oldest open `deindexed` or `site_not_indexed` alert with cause `clean`, actions and no `content_owner` whose page (a counterpart URL maps to its default-locale page via `alternate:`; a `site_not_indexed` alert offers its diagnosed URLs in order, one page per pick) is outside the cooldown, `exclude_slugs` and `skip` and was not rewritten since `assessed_at` (`pickAssessedPage`); the causes and actions become the diagnosis (`assessmentDiagnosis`, `improve.md` has an index-problem branch that trims sibling overlap and drops unsourced figures), `prepared.assessed` carries the alert id, a failed attempt gets the `failed` cooldown entry like a season. `seo run` does this also in weeks that generate pages, and when a season (or any other pick) holds the rewrite slot it prepares one extra assessed rewrite next to it (`prepareImprove({ assessedOnly, skip })`, `skip` = every page the first PR writes, so the two PRs never touch the same file; switch `assessed_rewrites: false`): events' Weihnachtsfeier and Silvester seasons would otherwise hold the slot until January. **Removal proposals** (`pickPrunePage`, `preparePrune`, switch `prune_proposals: false`): a page with an open `deindexed` alert (cause `clean`, no `content_owner`, no merge still to propose, no `prune_proposed_at`) that had at least 2 merged rewrites (`PRUNE_REWRITES`; failed, revert and prune entries do not count) with the last merge at least 60 days ago (`PRUNE_WAIT_DAYS`) gets one draft PR per run on `seo/prune/<slug>`: the page and its counterpart deleted and redirected (`buildMergeFiles`, no rewrite, no LLM call) to the assessment's `merge_into` or else the first indexed existing page of its `related_pages`; without an indexed target nothing happens. The gate holds the draft like a merge (deleting a live page is the owner's call), the alert gets `prune_proposed_at` so it proposes once, the improvements entry carries `prune: true` and never becomes a ledger entry. Report kind `prune` with `into`, followup `prune_proposed`. After the PRs `annotateFollowups` sets `followup` on every `report.assessments` entry: `rewritten` (with `pr_url`), `scheduled` (`not_before` = end of the cooldown), `owner`, `site` (site-wide alert) or `unmapped`; the mail shows that instead of the actions.

## Signals

**bing** (`src/lib/bing.js`, `src/lib/signals/bing.js`, opt-in `bing.enabled`, key `BING_WEBMASTER_KEY`): a second signal next to GSC, Bing feeds ChatGPT search and Copilot. `bingRequest` goes through `safeFetch` (15 s) and repackages every failure into `BingError({ method, kind, status })` with a fixed message, because `safeFetch` messages carry the URL and so the key; `kind` is `key_rejected` (400 with ErrorCode 3, 401, 403), `rate_limited`, `unavailable` or `error`; two failures in a row (or `key_rejected`) end the Bing calls of the process. `parseBingDate` maps dates before 2000 (Bing's year 0001) to `null`, and "crawled" means a real `LastCrawledDate`. The watcher calls Bing live (no cache): `GetUserSites` (site missing warns once, marker `bing.site_missing_warned`), `GetCrawlIssues`, and `GetUrlInfo` for 10 sitemap URLs a day (Bing throttles it after 10 per host with ErrorCode 5 ThrottleHost, read as `rate_limited`; `bingPicks`: URLs without a stored `bing.crawled` value first, then those stored `false`, two slots always recheck URLs stored `true`; each group sorted and rotated by `dayNumber * 10 mod count`, `dayNumber` from `today`). Booleans land in `alerts.json` under `bing.crawled` (pruned to the sitemap, with `issues_pending`, `site_pending`, `last_ok`). `evaluateWatch` takes one new input `bing`: `null` (off, no key, site missing) changes nothing, `{ error }` only feeds `bing_blind`, else `{ urls, issues, crawled }` drives `bing_crawl_issues` and `bing_site_not_crawled` (2-day hysteresis). Bing never counts towards `failures`/`watch_blind` and never lands in `errors`. `diagnoseAlerts` takes an optional `bing` client and sets `bing: { crawled }` on the URL entries, refreshed on every run when it changed, never part of `cause`/`codes`. `seo run` refreshes the queries weekly (`refreshBingQueries`, filtered before storing: no `@`, 6+ digits, phone numbers, over 120 characters, tracker probes); `generate` appends `bingQuestionsFor(keyword)` to `people_also_ask` at run time, `discover` uses them in the greenfield branch before `discoverGreenfield` (`source: 'bing'`, no cannibalization check since that needs GSC page rows). Not used by `improve`, `measure` or `traffic_drop`.

**rybbit** (`src/lib/rybbit.js`, `src/lib/signals/rybbit.js`, opt-in `rybbit.enabled` with `url`, `site_id`, `macro_goal`, `micro_goals`, key `RYBBIT_API_KEY`): what visitors do after the click, per landing page. Active only when the config is complete and the key exists (otherwise one warning). `rybbitRequest` sends the key as a Bearer header, talks https only, uses `redirect: 'manual'` and treats every 3xx as an error (following a redirect would hand the key to another host); failures become `RybbitError({ method, kind, status })` with a fixed message (`key_rejected`, `rate_limited`, `unavailable`, `error`), two in a row or `key_rejected` end the Rybbit calls of the process. The signal store caches the raw answers 7 days under `<site>:<endDate>:<kind>:<startDate>`; the window is the last 4 complete weeks (28 days) and ends on the last full Sunday so keys stay stable for a week; a dry run reads but never writes. `pageStats` (pure) groups entry pages over `urlToSlug` (path variants, query, locale). "Einstiege" are sessions that begin on the page. A goal is `null` (not measured, never 0) when the call failed, the name is not found or the goal has no conversion on the whole site in the window; `micro` is `null` as soon as one micro goal is. AI visitors are a lower bound (referrer or `utm_source` of known AI hosts, the larger of the two per path). `seo run` writes `report.rybbit = { window, totals, ai_sources, pages (top 10, 5+ entries), missing_goals }` or `{ error }` (the mail shows that as a task); goal calls only for the top 10 pages and pages with 30+ entries. Every `d28`/`d56` reading gets a `rybbit` field (`null` on failure) and later runs fill only that field for readings with `rybbit: null` (window younger than 90 days), never the verdict. `improve` multiplies the score of a GSC candidate by 1.25 with 30+ entries and known zero conversions (main and side goals), and always logs the Rybbit numbers in the reason; the improve and assess prompts get an engagement block only when the page had entries.

## Conversational queries

**conversational** (`src/lib/conversational.js`, `src/commands/conversational.js`): A reading instrument, not a pipeline step. Google folds AI Mode and AI Overview activity into the ordinary web search type and counts every follow-up turn as its own query, so conversation fragments, full natural-language prompts and AI-visibility-tracker probes land in the query table. The classifier is deterministic pattern matching into `artefact`, `tracker_probe`, `conversational` and `keyword`. Deliberately not wired into `discover`: making it an input is a separate decision.
