# src/steps: the run and improve pipeline

Path-bound rules for the pipeline steps of `seo run` and `seo improve`. Cross-cutting rules, commands and the state file table: root `CLAUDE.md`. Watcher, signals and lib modules: `src/lib/CLAUDE.md`. Prompt templates: `src/prompts/CLAUDE.md`.

## Pipeline steps

**discover** (`src/steps/discover.js`): Pulls the last 28 days of Search Console data (positions 8-25, filtered by `min_impressions`). Scores each candidate keyword via Claude + SerpAPI. Saves results to `seo/keywords.json` in the target project. Each keyword stores `serp_features` with `checked_at`; `getPending` orders by `serpPriority` (score minus 2 for informational intent with an AI Overview whose `ai_overview_cites_us` is exactly `false`, `null` means no evidence; features older than 60 days are ignored), the stored score stays unchanged. The SERP cache holds reference hostnames, `cites_us` is computed from the current `base_url` on read.

Three guards keep the backlog free of duplicates. `lib/similarity.js` rejects a candidate whose significant tokens match an existing keyword or slug (a word-order variant such as "webdesign freelancer preise" next to "freelancer webdesign preise") before it is scored. `lib/cannibalization.js` counts how many of our own landing pages already rank for that exact query and rejects the candidate from two up: the query is contested from the inside, and a new page joins that fight instead of winning it. For everything fuzzier, the scoring prompt receives the existing slugs and titles and returns `covered_by` when a published page already answers the question; that keyword is skipped with a note. Separately, `exclude_terms` (`lib/exclude-terms.js`, e.g. `[webflow]`) names services the site does not offer: a keyword or greenfield slug naming one (word start, case-insensitive) is skipped before any SERP or model call, from every source, and an already proposed keyword with such a term goes to `skip` at the start of discover. It exists because portfolio-2025 got three honest "I don't build with Webflow" pages from GSC demand: the style doc steers the text, this list steers the topics.

Greenfield (inventing keywords without GSC demand) is **opt-in** via `greenfield: true` and off by default. An empty backlog is a valid result: it means the topic space is covered. It used to top up whenever GSC yielded fewer keywords than `weekly_cap`, which guaranteed pages every week whether or not topics existed, and is how the target projects accumulated 70 pages for about 50 topics. Greenfield suggestions pass the slug, collision and word-order checks (against each other too) before any SerpAPI search, so a dropped suggestion costs no search.

New pages are capped per project and calendar month (`max_new_pages_per_month`, default 4; Google's scaled-content-abuse policy). `newPagesThisMonth` in `lib/keywords.js` counts keywords by `pr_opened_at` (open or merged, not rejected); `reconcileState` backfills the date from the PR's creation date. At 0 left the run skips discover (no SerpAPI or scoring spend) and goes to the improve path, which does not count.

**generate** (`src/steps/generate.js`): Calls Claude Opus (`MODELS.generate`, `GENERATE_MAX_TOKENS` = 32000, since adaptive thinking on Opus 5.5 counts against `max_tokens`; effort set explicitly to `high`, interactive calls carry the server-side `default` refusal fallback) with a prompt assembled from `src/prompts/generate.md` and a style doc. Outputs markdown with YAML frontmatter. Placeholders `CANONICAL_URL`, `BASE_URL`, `SITE_NAME` are replaced post-generation. The call goes through the Message Batches API by default (`batch_generation: true`, half the interactive price), falling back to an interactive request if the batch errors or does not finish within the wait cap; `--dry-run` forces interactive since a preview should not wait on a batch.

**validate** (`src/steps/validate.js`): Pure function, no I/O. Checks frontmatter fields, meta title/description lengths, FAQ count, body word count (800-1400), keyword density, entity coverage, em-dash/emoji, umlauts written as ae/oe/ue, fabricated-claim patterns, and on every project unsourced statistics (`STATISTIC`: a share of a group such as "70 Prozent der Gäste", "8 von 10", "jeder dritte", "laut einer Studie"; advice and terms such as "Puffer von 10 Prozent" are no statistic) without a link in the paragraph or a `sources:` entry (error `Unsourced statistic`; under strict a percent-sign sentence is already `Unsourced number` and not repeated). The events and topf-secret assessments named exactly these invented figures; `STATISTICS_RULE` in `generate.js` tells generate and improve. Returns `{ ok, errors, warnings }`. Up to 2 generation attempts per keyword.

**fact-check** (`src/steps/review.js`): Extracts checkable claims (laws, thresholds, deadlines, customs, brand and product names, third-party prices, cited studies) and verifies them with the server-side `web_search` tool, plus the tldr of every published page in the locale for cross-page number consistency. It also reads the page against itself: a price corridor, lead time or calculation that the tldr, FAQ and body state differently is a medium finding, and needs no search because the page is its own evidence. It also receives the project's style doc (the same one `generate.js` loads): a price or pricing rule that contradicts a canonical value there is a medium finding too, and the style doc outranks the sibling-page cluster when the two disagree, since the cluster can itself be wrong. Corrections apply only when the quoted text matches exactly once. A high-severity finding it could not patch drops the page; everything else is patched, revalidated and logged. A fact check that returns no JSON is retried once with an explicit JSON-only instruction; if it still fails, `reviewPage` returns `unchecked: true` instead of an empty finding list, `run` skips the page and the keyword stays `proposed` for the next run and `improve` keeps the rewrite but opens the PR with a warning that the facts were not checked. Off via `fact_check: false`, skipped in dry runs.

**verify** (`src/steps/verify.js`, prompt `src/prompts/verify.md`, `src/commands/verify.js`): the gate's independent second fact pass on the final PR head, no access to the first pass's findings, `quality: strict` only (others: `skipped`, exit 0). Reuses `runJsonCheck`, `parseFindings` and `applyFindings` from `review.js`. Rules: derived numbers are recomputed, law claims need the official wording in `statute_checks` (an entry without a quote becomes a blocking finding; a claim the model cannot quote is hedged by a patch instead, so a failed EUR-Lex/BMF fetch can drop a correct reference), verify gets `webFetch` and 20 searches/fetches per call (`VERIFY_MAX_SEARCHES`, the statute page itself from gesetze-im-internet.de), third-party prices need the vendor's page today (else the patch removes the figure). Every finding is blocking unless patched; a quote that recurs is replaced everywhere only when the finding sets `replace_all`. At most 2 rounds per page (round 2 only after a patch), `assertBudget` before each call, a verifier that cannot run or answers twice without JSON blocks (exit 3). Missing files (`--merge-from`), overlays and markdown outside the landing directories are skipped. `--commit` writes the patches through `commitToBranch` and prints `VERIFY_HEAD_SHA=<sha>`; `--pr` replaces the section between the `seo-verify` markers in the PR body (read-modify-write through `gh api`). Gate status `fact_blocked` (see `seo-reusable.yml`) is exit 3, a failed push, or a patch that breaks `seo check`. A `GITHUB_TOKEN` push triggers no PR workflow: a project with PR CI would hit `checks_timeout` (none today). `page_contract.forbidden_claims` is the deterministic counterpart (regexes, always an error, `validate.js`). Acceptance eval: `test/eval/verify-history.mjs` (real API, not in `npm test`). `seo live-check` (`src/commands/live-check.js`) reuses the watcher's `isLive`/`fetchLive` and `expectedLive`.

**pr** (`src/steps/pr.js`): One PR per keyword on `seo/new/<slug of the default-locale page>`, branched off and opened against the repo's default branch (`getDefaultBranch`), carrying all locale files and the counterpart of that keyword and nothing else (no state files, those go to `main` through `commitState`). `injectHreflang` runs over all pages of the run before they are grouped by keyword. The PR body has an SEO check table. The keyword entry stores `pr_url` and `sitemap_slugs`; the reconcile step at the next run sets it `published` when the PR is merged (closed without merge is `rejected` and never proposed again; `seo/sitemap-pending.json` is retired, `commitState` deletes it from the default branch). A branch that already exists (`BRANCH_EXISTS`, an open PR for the same keyword) skips that keyword with a warning and sets it back to `proposed`, one failing PR never stops the others. Branches never linger as orphans: a branch whose `openPR` failed is deleted right away (`deleteBranch`), and the reconcile step deletes the head branch of a PR that was closed without merge, so `BRANCH_EXISTS` only ever means a live PR. The gate that auto-merges such a PR also resubmits the sitemap to Google and, when `indexnow_key` is set, pushes all sitemap URLs to IndexNow (Bing, Yandex, Seznam, Naver) via `seo indexnow`.

**improve** (`src/steps/improve.js`, `src/commands/improve.js`): Runs when the backlog is empty, and standalone via `seo improve`. Aggregates live GSC page/query data per landing page of the default locale and picks the one with the strongest case. Scoring uses a page's *reachable* impressions, meaning those from queries at position 20 or better, not its total: the total counts long-tail queries at position 70 that no rewrite moves, and scoring on it sent the budget to pages that could not be helped (`onlineshop-erstellen-lassen`, 4690 impressions with 5 in reach, outranked `freelancer-webdesign-fuerth`, 786 with 759 in reach). A page with at least 30 percent of its impressions on page one whose CTR sits below half of what its position normally returns is a snippet problem (title and description); a page within reach of page one is a relevance problem; anything further out scores lowest. The CTR curve comes from published English-language studies, is not calibrated for German SERPs, and is used only to compare a page against itself. The rewrite gets the page's actual queries as context and may not claim services the page does not already claim. It also gets the project's style doc, with instructions that a price or pricing rule stated there overrides whatever figure the current page states. Rewritten slugs go into `seo/improvements.json` and are off the list for 56 days. The rewrite goes through the Message Batches API like `generate` (`batch_generation`), and `--dry-run` forces interactive; the fact check stays interactive because `complete()` rejects batch together with web search. The current page is validated first and its warnings and errors go into the prompt as `current_issues` (a headline without the keyword may be rewritten), so the rewrite fixes what the validator already flags; warnings that remain on the rewrite are listed in the PR body. When the rewritten page names an existing counterpart via `alternate:`, the counterpart is re-adapted from the checked rewrite (same slug, steps/checklist/faq counts must match) and ships in the same PR; if that fails twice the German rewrite is kept and the PR body says to sync by hand. The rewrite is split in `prepareImprove` (selection, rewrite, validation, fact check, no commit, no cooldown entry) and `publishImprove` (PR on `seo/improve/<slug>`, cooldown entry with `pr_url` only after the PR exists; `BRANCH_EXISTS` skips with a warning and sets no cooldown). `seo improve` runs prepare, `commitState`, publish, `commitState` (prepare sits inside the try/finally, so a budget or LLM error still writes the run log and commits state; a failing last commit is only logged and never replaces the original error); `seo run` calls the two halves itself. A merged rewrite PR keeps its cooldown entry (`merged_at` is set by the reconcile step), a closed one loses it. `seo improve --slug X --merge-from A,B` (`buildMergeFiles`, `lib/landings.js`) adds the merge to that PR: pages A and B deleted, `seo/redirects.json` entries to X (existing targets follow along), `related_pages` repointed. With `counterpart_locale`, the counterparts named by the merged pages' `alternate:` are deleted too and redirected to X's counterpart (else X), and `related_pages` of the counterpart locale are repointed.

Two cluster guards, added after an improve run pushed a page further into its neighbour's topic: `selectPage` drops every query another landing page ranks better for, before scoring, so a page is neither picked for nor rewritten towards impressions that belong elsewhere (the dropped ones are logged and kept on `page.foreignQueries`). For the fuzzier half, the prompt receives the slugs of all sibling pages and the instruction to trim, not extend, whatever reaches into their topics.

**queue** (`src/steps/queue.js` collects, `src/lib/queue.js` decides, `src/commands/run.js` executes; `seo/queue.json` and `report.queue`): `seo run` no longer follows a fixed `if` chain. `collectCandidates` asks every picker for one pick (`limit: 1`, `skip` = slugs earlier picks already take) and gives each candidate `{ type, slug, source, why, score, touches, pick }`; `touches` are all slugs its PR writes (page, counterpart, merge source or target). `buildQueue` (pure) ranks by type (revert 1, merge and prune 2, refresh 3, rewrite 4, snippet_test and faq 5, overlay 6, new_page 7; an assessed pick beats a GSC pick, then the score), dedups over `touches`, applies the locks and the cap `max_prs_per_run` (default 4, reverts included; one slot stays reserved for `new_page`, `snippet_test`, `faq` or `overlay`). Statuses: `selected`, `opened`, `deferred` (`cap`, `overlap`, `drafts_waiting`, `not_prepared`, `failed`, `not_opened`), `blocked` (`paused`, `brake`, `site_not_indexed`, `not_deployed`, `recrawl`, `open_pr`). Execution: reverts first (`revertWorseRewrites({ max: cap - 1 })`, so their cooldown entries exist before the pick), then the new pages as one batch, then every other entry in rank order through `prepareImprove({ pick })` (merge: `slug`/`mergeFrom`/`mergeAlert`, prune: `preparePrune`). Before each entry its `touches` are checked against the files already prepared (inbound-link edits included); an entry that yields nothing lets the next cap-deferred one move up, the cap counts prepared entries and opened reverts. Every type merges through the gate by itself (owner decision 2026-11-26) except `merge` and `prune` (`DRAFT_TYPES`, they delete and redirect live pages): those are draft PRs with the block "Warum diese Aktion" (type, source, reason, score) on top; `report.prs[].held` marks them and the improvements entry carries `held: true` (`prepared.auto`, default true outside the queue). `AUTO_TYPES` (`snippet_test`, `faq`, `new_page`, `overlay`) now only names the work that keeps the reserved slot. Locks (`buildQueue`): `paused: true` lets only reverts run; the brake (open `traffic_drop` whose `since` is 7 to 35 days after the newest ledger merge, ends with the alert or after 56 days with a warning) blocks `new_page`, `snippet_test`, `faq`, `refresh` and GSC `rewrite`, assessed rewrites go on; open `site_not_indexed` blocks `new_page`; open `not_deployed:<key>` blocks everything touching that slug; the recrawl lock keeps `rewrite`, `snippet_test` and `faq` off a page a merge or prune PR of the last 28 days pointed at until `index-status.json` shows a crawl after the merge (`isWaiting`, shared with the assessment in `src/lib/recrawl.js`; seasonal refreshes are exempt); a slug with an open PR in the improvements ledger is not chosen again, and from 3 held drafts on `merge`/`prune` wait (`drafts_waiting`). Types: `refresh` is `pickSeasonPage` or a stale page (`src/lib/refresh.js`: the highest year in meta title, description or H1 is below the current year, ignoring years after seit/ab/bis and spans like 2026/27 that have not ended, or `updated` older than 365 days; same exclusions as the seasonal refresh, one stale refresh per run); `snippet_test` is the GSC pick with `kind: 'snippet'` and at least 100 impressions (`MIN_TARGET_IMPRESSIONS`), written by `src/steps/snippet.js` (prompt `snippet.md`, `MODELS.default`, JSON `{ meta_title, meta_description }`, text edit of the two frontmatter lines, body byte for byte, only new validation errors or errors on the two fields count, branch `seo/snippet/<slug>`, `snippet: true` in the improvements entry, ledger kind `snippet`, measured and reverted like a rewrite); `faq` (switch `question_faq: false`, default on, also in weeks that generate pages; `src/lib/questions.js` picks, `src/steps/questions.js` writes, prompt `questions.md`): question and purchase-intent searches a page already shows up for and loses the click on, answered as FAQ entries. `questionKind` matches in code on Unicode word tokens (a GSC regex filter is RE2, where `\b` does not see umlauts): a German or English question word as first token or a trailing `?` is `question`, price/cost/buy/comparison/experience stems or words anywhere `purchase`. `questionGaps` keeps a page's own queries (`ownQueriesBySlug`, shared with `selectPage`) at position 20 or better with 10+ impressions and a CTR at least 50 percent below the position's norm; `pickQuestionPage` takes the page with the most such impressions (40 minimum, cooldown, `exclude_slugs`, `skip`, slugs of this run's new pages). One Opus call (JSON, interactive) gets the queries fenced, the current FAQ, siblings, the page, style doc, product facts, catalog and own figures, and either skips a query (off topic, a sibling's, already answered, or not answerable from those sources: nothing is invented) or writes an entry; at most 3 new entries, `replaces` -1 appends or names the index of the weakest entry it replaces, the cap is 6 under strict, else 8. `setFaqEntries` edits only the `faq:` block as text (refuses forms it cannot edit, checks the result parses to exactly the expected list); the counterpart (`alternate:`) gets the same entries at the same index in the same call, so the FAQ counts stay equal (a counterpart with a different count is a failure). Only new validation errors or errors on FAQ entries count, two attempts. The fact check runs on the page; unchecked, an unresolved high finding, or a patch inside the FAQ of a page with counterpart drop the action (failed cooldown entry), since nobody reads the PR before the gate merges it. Branch `seo/faq/<slug>`, `faq: true` in the improvements entry, ledger kind `faq`, measured and reverted like a snippet test; `--dry-run` prints the entries and the skipped queries. `overlay` is `prepareOverlay` (shop, recipes) when no landing page qualifies. The failed cooldown now also covers snippet, refresh and GSC rewrite picks. Every executed action stores `predicted: { type, score, basis }` in the ledger. Self-monitoring in `report.warnings`: entries selected but no PR opened, brake or pause active (with days), a held draft older than 14 days. `reconcileState` resubmits the sitemap once (`submitFixes`, after `isLive` with `watch.check_deploy`) for held drafts found merged in that run. `--dry-run` prints the queue in `report.queue` and writes no `seo/queue.json`.

**page contract, catalog, overlays** (shop projects, all opt-in, `src/lib/catalog.js`, `src/steps/overlay.js`, prompt `src/prompts/overlay.md`): `page_contract` in `seo.config.yaml` adds project rules to `validate` (`body_words` replaces 800-1400, `require`/`forbid` fields, `products` count, existence in the catalog and `max_overlap` against existing pages, `lowercase`, `meta_title_suffix` shortens the title limit, `facts_denylist` regexes fail unless the catalog states the match word for word), `reserved_slugs` are refused as slugs (validate and discover). `loadCatalog` (`catalog_url`, `safeFetch`, 10 s, once per process, shape check, `null` without the key) is the fact source: `run` loads it once and skips discover and generate while it is unreachable (improve and overlays too need it: overlays skip), `seo check` fails. `generate.md`, `greenfield.md` and `improve.md` get `{{catalog}}` (untrusted block) and `{{contract}}` (`pageRulesSection`, empty without configuration). `contractOptions(config, catalog, cwd, locale)` builds the extra `validate` options for run, improve and check. `discover` drops queries whose every page/query row sits under `/shop` (only with `overlays` set). Overlays: `overlays.products`/`overlays.categories` directories of `meta_title`/`meta_description`/`intro` files; `prepareOverlay` runs at the end of `prepareImprove` when no landing page qualifies (so `seo run` and `seo improve` both reach it), writes one overlay with `MODELS.default`, validates with `validateOverlay` (2 attempts, no fact-check call, the denylist against the catalog is the gate) and returns the same shape `publishImprove` takes, with a `branch` field (`seo/improve/product-<slug>`, a git ref cannot hold `:`). Start mode (no `/shop/` row in GSC), and any run where no shop page clears the impression floor: first catalog product without an overlay file. Keys `product:<slug>`/`category:<key>` (`overlayKey`/`parseOverlayKey` in `lib/improvements.js`) go into `improvements.json` and `changes.json`; `urlToSlug` maps overlay URLs to them (`overlay: true`, only when `overlays` is set), `normalizeUrl` keeps `?category=` on shop URLs, and the measure step takes controls of the same kind only. `seo check` routes files inside the overlay directories to `validateOverlay`. `watch.check_deploy: true` adds `not_deployed:<key>` alerts: `liveChecks` input of `evaluateWatch`, built from GitHub rather than the weekly-filled ledger: `listRecentlyMergedSeoPRs` (`lib/github.js`) lists PRs of `config.repo` on `seo/new/*` and `seo/improve/*` merged between 14 days and 24 hours ago, the key and URL come from the changed files (default-locale landing file of a `seo/new/` PR to its page URL, overlay file to its overlay key/URL); new pages by HEAD, 404 on two days in a row opens, overlays by GET and `<title>` containing `meta_title`; a GitHub error is a warning and leaves the alerts alone, `ok: null` (5xx, fetch failure, no local file) decides nothing, `watch()` takes injectable `fetchPage`, `listPRs` and `now`, state `deploy_pending` exists only while a check is pending, an open alert is re-checked by its stored URL after the 14-day window and resolves on a successful check, or as `removed` when its file is gone from disk. Overlay pages are left out of the landing page traffic totals, and an overlay target that fails validation twice gets the normal cooldown entry with `failed: true`. The watcher clears an alert's `resubmitted_at` when its diagnosis turns `technical`, so a later fix resubmits again (still at most every 7 days). The reusable workflow's `op_vault` input (default `development`) names the vault of the shared `seo-cli` item; every field, the Google pair included, comes from there.

**recipe overlays** (recipe sites without landing pages, today topf-secret; `overlays.recipes` plus `recipe_catalog_url`, `src/lib/recipe-catalog.js`, prompt `src/prompts/recipe-overlay.md`): the recipe pages come from the app's database, so their text around the recipe lives in one overlay file per recipe, `<overlays.recipes>/<slug>.md` (frontmatter `meta_title`, `meta_description`, `intro` as JSON strings so the backend reads them without a YAML parser, body = `notes`, the "Gut zu wissen" section, 2 to 4 plain paragraphs, 80 to 250 words; intro 30 to 80 words). Key `recipe:<slug>`, URL `<base_url><overlays.recipe_path, default /rezept>/<slug>` (`urlToSlug`/`overlayUrl`). Fact source is the recipe catalog (`{ version: 1, recipes: [{ slug, url, title, summary, servings, totalTimeMinutes, ingredients, steps, tags, dietTags }] }`, the published recipes as their pages show them, `loadRecipeCatalog`, 10 s, once per process). `validateOverlay` for a recipe: lengths (title minus `page_contract.meta_title_suffix`), no markup or links, no unsourced statistic, the recipe must be in the catalog, and every number of the text must appear in the recipe (`numbersNotInRecipe`: amounts, times, servings, step numbers; no calories, temperatures or times of its own). Selection in `prepareImprove`: an assessed `deindexed`/`site_not_indexed` alert whose URL is a recipe page (`recipeKeyForUrl` in `pickAssessedPage`, also `annotateFollowups`) goes straight to `prepareOverlay` with the assessment as `diagnosis`; otherwise the GSC pick finds no landing page and `prepareOverlay` takes the recipe page with the strongest GSC case, else the first recipe without an overlay. The assess prompt gets `RECIPE_SCOPE` for recipe pages (only the text around the recipe changes) and never asks for `merge_into`. `readLandingPages`/`getExistingPages` return `[]` without `landing_path`, so `seo run` works on such a site with `max_new_pages_per_month: 0`. `seo check` loads the recipe catalog for recipe overlay files.

**measure** (`src/steps/measure.js`, pure rules in `src/lib/measure.js`, ledger in `src/lib/changes.js`): runs right after the reconcile. `reconcileState` adds a `seo/changes.json` entry per merged PR (only with a real `mergedAt`; a separate backfill pass covers PRs merged in the last 90 days (by merge date) without an entry and retries unreadable ones; PRs that were read but never qualify, no real merge date or older, go to `skipped` in `changes.json` and are not read again; a rewrite stored without its counterpart gets the counterpart URL once the `alternate:` is on disk). Each due reading (`d28` = merge+8..+35, `d56` = merge+36..+63, baseline merge-28..-1, due 3 days after the window ends) costs up to three `queryPageTotals` calls, no LLM. New pages get absolute values; rewrites a verdict against control pages (same language, no ledger entry merged in merge-28..merge+63), strict rules: 90th/10th percentile of `r` plus 1.3x/0.7x the median, at least 12 controls, `insufficient_data` reasons `volume` (baseline only, so a collapsed page stays measurable)/`control`/`dispersion`/`overlap`/`missing` (target had a baseline but no GSC row in the reading window, never read as zero). A target URL that maps to no landing page gets `unmapped: true` once and is never measured (counted under `unmapped`). `d56` is only computed once `d28` exists. With fewer than 12 landing controls the other site URLs of the GSC rows join them (`controls_source: 'site'` on the reading, dispersion limit halved, never a `revert_candidate`). Two negative readings with effect <= 0.7 set `revert_candidate` and warn. **revert** (`src/steps/revert.js`, Etappe C, switch `auto_revert: false`, default on): right after measure, `seo run` (not dry runs) takes back every `rewrite` entry with `revert_candidate` and no `revert` field: the files of the rewrite PR named after the page and its counterpart (`pageNames` from `urls` and `slug`; other pages' link edits stay) go back to their content at the merge commit's first parent, in one PR on `seo/revert/<slug>` that goes into `report.prs` as kind `revert` and merges through the gate like any other (owner decision 2026-11-26). Never when the PR removed or renamed files (`deletes_or_moves_pages`), when a file changed on the default branch since the merge (`changed_since`, blob sha against the merge commit), or when the old version fails the gate's `seo check` rules (`previous_version_fails_check`, local `validate`, skipped for catalog/overlay projects). The decision lands on the ledger entry as `revert: { status: opened|skipped|superseded, date, pr_url?, reason? }` and is never revisited; `superseded` = the page was rewritten and merged again after it; an open rewrite PR of the page and GitHub errors (also `BRANCH_EXISTS`) leave no mark and retry next run. An opened revert writes an improvements entry with `revert: true` (normal cooldown, before the improve pick so the page is not rewritten in the same run; not a refresh for the 300-day season rule) and its merge becomes ledger kind `revert`, measured like a rewrite but never a revert candidate itself. `report.reverts` lists every decision. A window without any landing page impressions is an error: warning, nothing saved. Errors never stop the run, `--dry-run` writes nothing. Result in `report.measurement` (counts and this run's changes only).

**track** (`src/steps/track.js`): Appends GSC page/query performance to `seo/rankings/YYYY-WW.csv`. Gitignored in target projects.

## Seasons

**Seasons:** `seasons: [{ name, peak: 'MM-DD', lead_weeks: 10, keywords: [], pages: [slug] }]` in `seo.config.yaml` (default `[]`), for sites without GSC history. `activeSeasons` (`src/lib/seasons.js`) returns the seasons whose window `[peak - lead_weeks * 7 days, peak]` contains today (nearest upcoming peak, year wrap works, UTC dates), nearest peak first, with `peak` as YYYY-MM-DD; malformed entries are skipped with a warning. discover scores season keywords not yet in `keywords.json` through `scoreAndSave` (same duplicate, cannibalization and slug guards, `source: 'season'`, `season: <name>`), independent of `greenfield`, never re-scoring a known keyword; the `{{season}}` placeholder of `score.md` renders empty for every other keyword. They count toward `max_new_pages_per_month` like any proposed keyword. improve: `pickSeasonPage` takes the first listed page of an active season that exists, is not in `exclude_slugs`, is outside the 56-day cooldown and was not successfully rewritten in the last 300 days, and it wins over the GSC pick (reason `Saison <name>, Peak <date>`, via `targetedPage`). `seo run` adds `report.seasons = [{ name, peak, seeded, refreshed }]` (new season keywords that were not skipped; slug of the published seasonal rewrite or null). In `seo run` a seasonal rewrite also runs in weeks that generate pages; the GSC pick stays limited to empty-backlog weeks. A seasonal rewrite that ends without a PR records a `failed` improvement entry (56-day cooldown, not a refresh for the 300-day rule).

## Multi-locale support

When `config.locales` has more than one entry, `generateForLocale` runs for each locale. The `landing_path` is rewritten by substituting the locale segment (e.g. `/de/` to `/en/`). `pr.js` injects `hreflang` blocks into frontmatter for multi-locale pages.

## Counterpart-locale support

A separate, orthogonal model from multi-locale: when `config.counterpart_locale` is set (e.g. `en`) and differs from the default locale, every successfully generated+validated default-locale page also gets a counterpart page (`src/steps/counterpart.js`, prompt `src/prompts/counterpart.md`). Unlike multi-locale hreflang pages, the counterpart gets its **own** slug (chosen by the model, checked for collisions across both locale directories) and both pages share the bare `/{slug}` URL space (no locale prefix), reciprocally linked via an `alternate:` frontmatter field (`linkAlternates` in `counterpart.js`). `validate()` accepts a `{ counterpart: true }` option that skips the German-specific denylist and source-keyword/entity checks for the adapted page while keeping structural and brand-casing checks. A counterpart failure after 2 attempts is logged and skipped. In `run` the pair ships together or not at all: the keyword stays `proposed` and becomes `validation_failed` (with a `note`, counter `counterpart_failures`) after the second dropped run; in `improve` the rewrite is kept and the PR says to sync by hand. `improve` reuses this flow through `generateValidatedCounterpart` (`src/steps/counterpart-loop.js`) with `fixedSlug`, so the existing counterpart keeps its slug. Both `run` and `improve` pass `matchCounts: true`, so a counterpart whose steps/checklist/faq counts differ from its source is a validation error and gets one retry (the site's landing-sync test requires equal counts).
